# Shopify fulfillment invoicing

Implemented against `master` / `origin/master` at `4b06bd66418a4e175b1988c57db61c6e00c8b558`.
No production migration, recovery apply, invoice creation, webhook registration, or deployment was performed during implementation.

## Behavior and settings

Admin Settings → **Invoice Creation Trigger** persists under `system_settings.orders`:

| Option | New-order behavior |
| --- | --- |
| Shopify Fulfilled | Paid creates the KiotViet order with `makeInvoice:false`. Live Shopify full fulfillment admits a separate invoice job. |
| Shopify Paid | Paid creates the order first, then admits the same validated invoice job. Partial fulfillment still requires review. |
| Disabled | No new automatic invoice jobs. Order/customer/product synchronization continues. |

Fresh installations default to Fulfilled. Existing installations with no explicit trigger retain the old `autoInvoice` behavior until the administrator selects an option. In particular, a legacy installation with `autoInvoice:true` continues its existing makeInvoice-on-order behavior. Explicit trigger selection disables that old path; the UI also writes `autoInvoice:false` for safe rollback.

The server assigns `invoiceTriggerEnabledAt`; clients cannot backdate it. Changing triggers advances the cutoff. Only Shopify orders **created after** that cutoff are eligible. Existing orders, including #1072, do not become eligible when a trigger is enabled. Disabling and re-enabling deliberately excludes orders from the previous activation period. Currency and default branch must be configured, and the branch needs an enabled Shopify location mapping.

Orders/create, orders/paid, orders/updated, fulfillments/create, and fulfillments/update feed the existing worker. Order completion rechecks eligibility, covering fulfillment before the KiotViet order exists. A minute scheduler checks at most 50 mapped post-activation candidates per run, rotating unfulfilled candidates every five minutes. It checks live Shopify state, so a missed webhook is not the only trigger.

`sync_jobs` has one permanent invoice job per Shopify order. PostgreSQL is the outbox; an interrupted Redis handoff is retried using the same BullMQ ID. Redis/worker must be enabled for automatic invoice execution; Redis-disabled mode retains pending outbox rows. Failed/manual-review invoice jobs are retained for operator inspection, not regenerated by duplicate webhooks. Replay the existing job after resolving a definite validation failure; never delete invoice mappings to retry.

The existing recovery planner performs financial validation and invoice lookup. Its short advisory-lock transaction and unique invoice mappings claim the attempt; HTTP calls happen outside PostgreSQL transactions. `creating` means the POST may have happened. Unknown outcomes are reconciled, never automatically reset or blindly POSTed again. Existing invoices are linked, including staff invoices. Cancelled invoices prevent automatic replacement.

Invoice existence, invoice financial checks, branch stock movement, and Shopify stock synchronization are distinct evidence. `reconciliation` stores before/after stock, expected quantities, branch, invoice status, validation checks, and Shopify synchronization results. A branch stock mismatch is `needs_review`, even if the invoice exists. A linked staff invoice generally has no pre-invoice baseline and therefore needs inventory review. Never create another invoice to repair stock verification.

Shopify receives **absolute current KiotViet on-hand**, subject to the existing safety stock, conflict policy, compare-and-set, and readback checks. No fulfilled quantity is subtracted again. Stock refresh and writes are serialized per branch/product using a session advisory lock, without an open transaction. Missing authoritative stock causes retry rather than fallback to stale webhook quantities. Product-triggered and scheduled inventory synchronization also refresh under that lock. Configure the PostgreSQL pool with headroom for lock sessions plus normal query connections.

App invoice records block reverse fulfillment, including invoice notifications carrying tracking. Staff-only reverse synchronization continues to respect the existing direction setting. No product return/restock policy is introduced.

## Lookup limits and remaining uncertainty

The [KiotViet retail API, section 2.12](https://www.kiotviet.vn/huong-dan-su-dung-kiotviet/retail-ket-noi-api/public-api/) documents `orderId`, branch/customer filters, offset pagination and totals, but describes the retail `orderId` filter ambiguously. This implementation does **not** silently assume an empty orderId response proves absence.

OrderId and branch/customer queries find likely existing invoices quickly. Absence requires a complete retailer-wide scan: stable reported total, explicit orderCode fields (null is allowed), valid unique IDs, no empty premature page, actual returned-count offsets. No purchase-date lower bound is used because invoices can be backdated. Each invoice-list request has an 8-second timeout and one attempt, with phase, offset, total, returned-count and duration diagnostics on stderr. The scan stops at 10 pages, a 25-second scan budget, or a reported catalog over 1,000 invoices (the last request can extend the budget by up to 8 seconds; authentication has its own timeout).

**For retailers with more than 1,000 invoices, this deliberately blocks new automatic invoices with `invoice_lookup_incomplete` until a reliable provider order-filter contract is established.** It fixes the unbounded/sluggish lookup behavior, not the provider ambiguity. Do not raise limits or trust a scoped empty response just to force invoice creation. Confirm filter semantics with KiotViet and implement/test that documented contract before relaxing this guard. Existing invoice IDs found by hints can still be linked, with incomplete uniqueness recorded for review.

There is no documented reliable invoice POST idempotency key here. Application claims prevent concurrent application POSTs for the same attempt. A staff member or another integration can still create an invoice between the final lookup and POST. Pagination is not a remote snapshot; concurrent remote edits may escape a stable-total check. Shopify cancellation/refund can also race the final read. These are not claims of perfect cross-system idempotency. Coordinate staff invoicing with the automatic workflow and investigate ambiguous outcomes.

The live [Shopify Admin Order API](https://shopify.dev/docs/api/admin-graphql/latest/objects/Order) provides the financial and fulfillment snapshot. Bounded snapshots currently allow 100 order lines, 20 shipping lines, 100 refunds, and 100 lines/transactions per refund; truncation requires review. Refund details are fetched separately to limit GraphQL query cost. Unsupported shipping, discounts, additional tax, tips, product refunds, currency differences, missing payment evidence, and inconsistent prepayments block creation. Processing-fee-only refunds remain distinct from product refunds.

Exact before/after stock movement is supporting evidence, not a transaction-level stock ledger: concurrent sales or manual adjustments may either mask or change the observed difference. Inconclusive attribution requires manual review using the KiotViet branch movement ledger. No automatic restock or reset of an uncertain invoice attempt is performed. The existing explicit CLI `--reset-uncertain` remains an operator-only action and must never be used by automation.

## Migration and PM2 deployment (operator procedure; not executed)

Use a maintenance window, back up PostgreSQL/Redis, and stop all old worker processes before installing the release. Migration 008 adds a candidate-check timestamp and indexes; it retains every mapping and job. The migration runner uses a transaction, so indexes are not built concurrently: allow maintenance time for the existing job table. No cleanup DELETE runs in the migration.

From `/var/www/shopify-kiotviet`, with the production environment file already provisioned:

```bash
pm2 stop shopify-kiotviet-worker shopify-kiotviet-scheduler shopify-kiotviet-web
# Install the reviewed release files using your normal release process.
npm ci
npx tsx --env-file=.env.production scripts/migrate.ts
npm run typecheck
npm test
npm run build
npx tsx --env-file=.env.production scripts/register-shopify-webhooks.ts
NODE_OPTIONS="--env-file=/var/www/shopify-kiotviet/.env.production" pm2 restart ecosystem.config.js --update-env
pm2 save
pm2 logs shopify-kiotviet-worker --lines 100
```

Confirm webhook registration succeeded for the new paid/fulfillment topics and verify the `fulfillment-invoices` scheduler registration. The web app, worker and scheduler must use the same release, PostgreSQL, Redis, and credentials. Retain existing direction settings. Select Fulfilled explicitly on an existing installation only when ready to test new orders.

Cleanup now deletes at most 500 eligible rows per table per daily run, with `SKIP LOCKED`. It never deletes failed/manual_review jobs or permanent invoice jobs. A large backlog will take multiple maintenance runs; do not replace this with an unbounded DELETE.

## One-new-order safe test

Use a development Shopify store and KiotViet test retailer first. Do not use #1072. If testing production later, obtain normal business authorization for the one actual sale/invoice.

1. Configure currency, branch/location mapping, safety stock and conflict strategy; choose Fulfilled. Note the activation timestamp and current stock at that branch/location. Check the retailer lookup can establish completeness; otherwise expect review, not an invoice.
2. Create a new paid, unfulfilled order after activation, with one mapped SKU, no shipping/discount/tax/tip, and optionally the configured SVC fee.
3. Confirm exactly one `order_mappings` row/KiotViet order, `makeInvoice:false`, no invoice and no KiotViet on-hand deduction. Confirm the fee is absent from KiotViet items/payment.
4. Fulfill it in Shopify. Confirm the job reads current Shopify status, then creates or links exactly one invoice against the original KiotViet order ID. Confirm no additional payment where the order was prepaid.
5. Inspect `invoice_mappings.reconciliation`: correct branch, expected lines, stockBefore/stockAfter, invoice status, checks, stockVerified and shopifyStockSynchronized. Check Shopify absolute quantity equals current KiotViet stock adjusted for configured safety stock. If either stock check is inconclusive, investigate manual review; do not invoice again.
6. Replay the same fulfillment notification and an older stock notification. Confirm the same order/invoice IDs remain and stock is not subtracted again. In a separate sandbox test, omit the fulfillment webhook and verify scheduler recovery.

Read-only inspection (substitute the new Shopify order ID):

```sql
SELECT shopify_order_id,kiotviet_order_id,kiotviet_order_code,status
FROM order_mappings WHERE shopify_order_id='NEW_ORDER_ID';
SELECT kiotviet_invoice_id,kiotviet_invoice_code,status,last_error,reconciliation
FROM invoice_mappings WHERE shopify_order_id='NEW_ORDER_ID';
SELECT id,status,error,payload FROM sync_jobs
WHERE type='shopify_invoice_create' AND payload->>'entityId'='NEW_ORDER_ID';
```

## Rollback and manual reconciliation

Set Invoice Creation Trigger to Disabled and allow active calls to finish; then stop workers/scheduler. Preserve PostgreSQL invoice/order mappings, permanent invoice jobs and all uncertain attempts. Leave additive migration 008 installed. Keep the current release available to inspect/reconcile pending outcomes. Do not reset creating/needs_review rows, delete claims, or retry POST to make rollback simpler.

Remove the `fulfillment-invoices` recurring BullMQ scheduler using `getQueue('reconciliation').removeJobScheduler('fulfillment-invoices')` from an operator script with the configured environment. With the current code and Disabled setting, drain any already-enqueued new invoice jobs before reverting worker code (or keep the worker stopped); old workers do not understand the new job types. Retain the audit rows. Restore the previous reviewed release and rebuild, then use the PM2 restart command above. Leave `orders.autoInvoice:false` until an administrator explicitly chooses to restore legacy paid invoicing. Do not roll back by cancelling real invoices or restocking automatically.

For stock review, compare the invoice branch/quantities against KiotViet's movement ledger and intervening sales/adjustments. Reconcile the existing inventory conflict through Admin, then replay the existing stock synchronization job to refresh absolute stock. Invoice existence alone is not proof of the original stock movement. If attribution remains inconclusive, retain `needs_review` and the evidence; no replacement invoice is required.
